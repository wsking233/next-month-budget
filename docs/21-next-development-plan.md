# 下一轮开发计划

日期：2026-10-18。基线：v0.6.0，原 Phase 1–6 已完成。

本文是下一轮建议，不代表未定业务规则已经获批。初次任务仅规划；随后按自动开发目标执行。第一阶段以 v0.7.0 交付，第二阶段按确认的固定金额规则以 v0.8.0 交付，第三阶段在还款范围确认后以 v0.9.0 交付；最终候选版本按验收范围决定。

## 目标与顺序

将现有账务闭环推进到可以持续日常使用：先降低首次建账和重复操作成本，再完善收入计划、信用卡与还款管理。延续纯前端、本地数据、整数分、追加审计及保存成功才更新界面的约束。

| 顺序 | 拟定版本 | 目标 | 前置条件 |
| --- | --- | --- | --- |
| 1 | v0.7 | 首次建账与日常操作体验 | 可直接按现有规则实现 |
| 2 | v0.8 | 周期预算模板与收入分配 | 明确收入分配及不足额处理规则 |
| 3 | v0.9 | 信用卡账户与还款管理 | 明确日期、部分还款及历史账户迁移规则 |
| 4 | v1.0 候选 | 完整使用场景验收与稳定性 | 上述阶段验收通过，明确首版范围 |

## 第一阶段：首次建账与日常操作体验

优先解决新用户面对空账本不知道从哪里开始，以及已有用户查找账单和审计记录费力的问题。

范围：
- 首次使用展示「创建周期 → 创建资金池 → 拨款 → 记录并结算账单」步骤及入口，完成状态由现有账本推导。
- 清楚区分空账本、演示模式、已有本地账本、读取失败，损坏数据继续提供原始文件下载与恢复入口。
- 账单支持按状态、账户文本、到期日期范围筛选；审计记录支持按事件类型筛选，提供清空筛选及无结果状态。
- 表单提供明确的校验定位、成功反馈和保存失败后的重试体验；沿用现有财务规则。
- 主题偏好跨刷新保留，偏好存储失败不阻断账本操作。
- 备份区域清楚展示当前账本保存状态、导出入口，以及 JSON 未加密和仅保存在此浏览器的说明。

验收：
- 空浏览器可完成建账、拨款、结算、刷新恢复、导出、导入全过程；引导不会重复创建数据。
- 筛选只改变展示，不改变结算结果、余额、审计或导出内容。
- 损坏存储、配额不足、旧标签页写入冲突时，旧数据和未提交输入受到保护。
- 手机窄屏、键盘、浅深色及三浏览器的新增流程通过检查。

此阶段优先复用快照版本 1，无数据模型变化时不增加迁移机制或升级格式版本。

## 第二阶段：周期预算模板与收入分配

现有拨款是直接记入资金池的操作；下一步需要表达「计划」与「本次实际拨款」，减少每周期重复输入。

先明确：
1. 使用固定金额、收入比例，还是允许两者组合？收入不足时优先级及缺口如何处理？
2. 多笔收入、奖金如何归属周期？重复点击应用计划怎样识别？
3. 计划储蓄是否仅为目标？建议首轮作为计划指标，不能显示为实际银行存款。

规则确定后实现：
- 周期预算模板与复制上期计划；模板编辑不修改历史流水。
- 实际收入记录及分配预览，显示收入、拨款、计划储蓄和未分配金额之间的关系。
- 用户明确提交后生成拨款及审计；单次提交整体保存，失败不留下部分流水。
- 模板重复应用有明确防重机制；历史修正采用可追溯操作。

验收：收入不足、额外收入、跨周期、整数分舍入、重复提交、撤销或更正都有确定规则及领域测试；统计明确区分计划、实际收入与预算拨款。

本阶段如需新快照版本，先实现旧版本迁移、迁移后完整校验和失败保全，再接入新字段。迁移路径与可恢复格式必须有测试，不能直接放宽当前严格校验器。

## 第三阶段：信用卡账户与还款管理

将当前账单中的账户文本升级为可维护的信用卡账户，并独立记录实际还款。

先明确：账单日和还款日遇到月末如何处理，是否支持部分还款与超额还款，旧账户文本如何确认合并。节假日顺延、退款、利息及分期不得静默推断。

规则确定后实现：
- 信用卡账户新增、编辑、停用；历史账单保留关联。
- 到期列表及页面内提醒，区分账单结算状态与实际还款状态。
- 还款记录、撤销及审计；还款不再次扣减资金池预算。
- 旧账单账户迁移预览与明确映射，避免误合并同名账户。

验收：同一账单先结算后还款、先还款后结算均不重复扣预算；账户停用不破坏历史；月末日期、重复还款提交、历史迁移及备份恢复有覆盖。

银行连接、系统推送和现金资产自动对账不纳入本阶段。

## 第四阶段：首版候选验收

- 用不含真实敏感信息的验收账本走完连续三个周期：收入分配、负数结转、跨期拆分、调拨、更正、撤销、还款、导出恢复。
- 对照 PRD 逐项标记已交付、待定及延期；原六阶段完成不等于所有 PRD 条目完成。
- 校验旧快照升级、新快照恢复、写入失败及多标签页冲突，确认账务守恒和审计可追溯。
- 进行手机实际设备人工验收；Playwright WebKit 结果不能替代 Safari 真机结论。
- 保留现有 lint、类型、单元测试、构建及三浏览器 CI 门禁。修复影响金额、数据安全和关键操作的问题后，再决定是否标记 v1.0。

## 后续候选，不与上述阶段并行扩张

出账前预算预占、退款与分期、非信用卡支出、防重复归集、备份加密、PWA/离线资源缓存。每项先形成业务示例和规则，再排入开发；继续不引入后台、登录或银行接口。

## 执行与发布约定

仅使用 main 分支；每阶段按「规则与交互 → 领域/存储 → 界面 → 验收 → 发布」完成。仅为新风险及新增行为补充必要测试。业务规则变化同步 PRD、业务规则及决策记录。

应用阶段验收后单独提交、记录版本并推送，由既有 Actions 发布 Pages。日常不查询 Actions 状态 API；异常时再排查。规划文档本身不触发版本升级；应用按实际验收阶段发布。

当前前三阶段已交付。连续三周期技术验收已通过；正式 v1.0 标签待实际使用反馈与真机人工验证。退款、分期、PWA 等不在本轮确认范围内，不阻塞已确认功能交付。
